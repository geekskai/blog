# OP-001 Investigation Plan

**Opportunity:** Quota Gate users do not start signup  
**Created:** 2026-09-15  
**Evidence snapshot:** Product Growth Review completed 2026-09-13  
**Phase:** MEASURE → INVESTIGATE → VALIDATE  
**Status:** INVESTIGATING  
**Explicit exclusions:** No feature build, redesign, pricing change, paywall change, or A/B test.

## Decision to Unlock

Determine what users do immediately after the existing download Quota Gate appears, which observable path accounts for the largest share of the 81.40% Gate → Signup Start drop-off, and whether the loss happens before an explicit choice, during navigation, or after signup begins.

This investigation does not select or propose a solution.

## 1. What We Already Know

From the 30-day UTC window ending 2026-09-13:

| Stage | Unique journeys | Conversion from prior stage | Drop-off |
| --- | ---: | ---: | ---: |
| `quota_gate_viewed` | 1,763 | — | — |
| `signup_started` | 328 | 18.60% | 81.40% / 1,435 journeys |
| `new_account_completed` | 157 | 47.87% | 52.13% / 171 journeys |
| `successful_download` within 24h | 132 | 84.08% | 15.92% / 25 journeys |

Additional confirmed facts:

- Gate → Activated Registration is 132/1,763, or 7.49%.
- The largest measured loss is before `signup_started`.
- Once a new account is completed, the existing return-to-tool flow leads to a successful download within 24 hours for 84.08% of this cohort.
- A Visitor receives 3 daily successful downloads; a Registered User receives 10; one eligible X Share Unlock adds 5 for the UTC day.
- The current gate offers four observable destinations or actions: create account, open the X share path, open Audio Toolkit Pricing, and close the gate.
- Audio Toolkit payment does not increase the public download allowance. The Pricing path must therefore remain analytically separate from quota recovery.
- Existing first-party event authority is Neon. Clarity is diagnostic only.
- Existing raw linkable growth events are retained for 90 days.

## 2. What We Do Not Know

1. The first action selected after each gate view: signup, X share, Pricing, dismiss, or no observed action.
2. Whether `signup_started` represents nearly every signup CTA selection or loses events during page navigation.
3. How often the same journey sees the gate repeatedly before acting.
4. Whether X Share Unlock is selected and granted, selected but rejected, or selected without a later successful download.
5. Whether Pricing visitors return to the original download task.
6. Whether the drop-off is concentrated in a specific `tool_id`, locale, device category, user state, quota mode, or gate reason.
7. How long users remain at the gate before acting or leaving.
8. Whether a user who appears inactive in the original session completes signup or downloads later through another session.
9. Whether close/dismiss represents task abandonment, postponement, or an alternative path outside the measured window.

## 3. Decision-Blocking Unknowns

The investigation cannot enter Solution stage until it resolves these questions:

1. **Outcome allocation:** What percentage of unique gate journeys selects each mutually exclusive first action?
2. **No-action loss:** What percentage records no action within the defined decision window?
3. **Delivery integrity:** Does `signup_started` reliably arrive before navigation, or is part of the 81.40% an event-delivery artifact?
4. **Segment concentration:** Is the dominant loss broadly distributed or concentrated in a tool/device/locale/quota-mode segment with an adequate sample?
5. **Recovery result:** For each action path, what percentage completes a successful download within 24 hours?

## 4. Data Required

For each unique first-party `journey_id` entering the cohort, collect or derive:

- First eligible Quota Gate timestamp.
- A gate-instance identifier for distinguishing repeated modal openings within one journey.
- First gate action and its timestamp.
- Whether a Share Unlock was actually granted.
- Whether signup navigation began, an account was completed, and the original tool was restored.
- Whether a server-confirmed successful download occurred within 24 hours of the first gate view.
- Controlled segmentation fields: tool, locale, device category, user state, quota mode, gate reason, allowance state, and copy variant.
- Event delivery status sufficient to separate “no action” from a failed client transmission.

Do not collect media URLs, pasted URLs, filenames, email addresses, IP addresses, PayPal identifiers, raw Clerk IDs in analytics tools, or other user input/PII.

## 5. Required Events

### Existing events to retain

| Event | Authority | Investigation use |
| --- | --- | --- |
| `quota_gate_viewed` | Neon first-party growth event | Cohort entry; deduplicate repeated views by journey while retaining gate-instance count |
| `signup_started` | Neon first-party growth event | Confirm signup path initiation before navigation |
| `new_account_completed` | Neon + Clerk return classification | Confirm a newly created account within the existing return window |
| `signin_completed` | Neon + Clerk return classification | Keep returning-account behavior separate from new signup |
| `share_intent_opened` | Neon first-party growth event | Diagnose X share selection intent |
| `share_channel_opened` | Neon first-party growth event | Diagnose composer-open behavior; not proof of publication |
| `successful_download` | Server/product-domain fact | Confirm the interrupted job was completed |

### Missing investigation events

| Event | Trigger | Why required |
| --- | --- | --- |
| `quota_gate_action_selected` | A user selects create account, X share, Audio Pricing, or close on the existing gate | Assign a mutually exclusive first observed gate action without inferring intent |
| `quota_gate_unlock_resolved` | The existing quota authority returns the result of an unlock attempt | Separate a granted allowance increase from share intent, composer open, rejection, or failure |

No `signup_abandoned`, `user_confused`, `paywall_rejected`, or similar inferred event should be emitted. Abandonment/no-action is derived from the absence of a later fact event within the defined window.

## 6. Event Properties

### Common controlled properties

| Property | Type / allowed values | Applies to | Purpose |
| --- | --- | --- | --- |
| `journey_id` | Opaque UUID; first-party only | All events | Connect pre-auth and post-auth facts without PII |
| `gate_instance_id` | Opaque UUID | Gate view and gate action | Distinguish repeated gate openings in one journey |
| `tool_id` | Existing controlled `QuotaToolId` | All events | Compare existing quota tools |
| `occurred_at` | UTC timestamp | All events | Order facts and calculate time-to-action |
| `user_state` | `visitor`, `registered` | Gate events | Keep anonymous and authenticated allowance paths separate |
| `locale` | Supported locale code | Gate events | Detect localized concentration without storing free text |
| `device_category` | `desktop`, `mobile`, `tablet`, `unknown` | Gate events | Controlled diagnostic segmentation |
| `quota_mode` | `server`, `local` | Gate events | Separate first-party-authoritative and fallback behavior |
| `gate_reason` | `daily_limit_reached`, `share_required`, `unknown` | Gate view | Distinguish current code paths that open the gate |
| `remaining_before_gate` | Non-negative integer bucket or exact controlled allowance value | Gate view | Confirm the gate appeared at the expected allowance state |
| `daily_limit` | Controlled integer | Gate view | Interpret Visitor vs Registered allowance contract |
| `share_eligible` | Boolean | Gate view | Identify whether X Share was actually available |
| `copy_variant` | Controlled value; current baseline is `baseline` | Gate view/action | Prevent mixing future copy states; not authorization for a test |

### Action-specific properties

| Property | Type / allowed values | Event |
| --- | --- | --- |
| `action` | `signup`, `share_x`, `audio_pricing`, `dismiss` | `quota_gate_action_selected` |
| `action_rank` | Positive integer within a gate instance | `quota_gate_action_selected` |
| `unlock_method` | `share_x`, `account_registration`, `account_signin` | `quota_gate_unlock_resolved` |
| `unlock_amount` | Controlled integer | `quota_gate_unlock_resolved` |
| `grant_result` | `granted`, `already_used`, `not_eligible`, `failed` | `quota_gate_unlock_resolved` |

`action_rank=1` defines the first observed action for the diagnostic branch split. Later actions remain available for journey reconstruction but do not change the first-action classification.

## 7. Funnel Definition

### Primary signup funnel

Use unique `journey_id` and the first eligible gate view during the observation window:

```text
First quota_gate_viewed
  → first quota_gate_action_selected(action=signup)
  → signup_started
  → new_account_completed within the existing 1-hour return classification
  → successful_download within 24 hours of the first gate view
```

Report conversion, drop-off, absolute lost journeys, and median elapsed time for each adjacent stage.

### Diagnostic first-action branches

```text
First quota_gate_viewed
  ├─ signup
  ├─ share_x
  ├─ audio_pricing
  ├─ dismiss
  └─ no observed action within 30 minutes
```

For each branch, report:

- Share of unique gate journeys.
- Successful Download within 24 hours.
- Repeated gate view within 24 hours.
- New account completion where applicable.

`no observed action` is a derived classification, not a client event and not proof of user intent.

### Counting and comparison rules

- Primary denominator: unique `journey_id` with a first eligible `quota_gate_viewed` during the window.
- Repeated gate instances are diagnostic and do not create additional primary-funnel users.
- First action is the earliest valid action after the first gate view and before another gate instance or the 30-minute decision-window end.
- Server-confirmed `successful_download` is the result authority.
- `share_channel_opened` proves composer open only; it does not prove publication.
- Audio Pricing navigation is not a quota unlock and is not counted as signup or payment.
- Segment comparisons require at least 100 unique journeys in each reported segment; smaller groups are displayed as small-sample observations and do not drive a decision.

## 8. Observation Period

Observe for a minimum of:

- **14 complete UTC days**, and
- **200 unique eligible Quota Gate journeys** after the investigation events are verified.

Both thresholds must be reached. This preserves the existing decision contract in `docs/adr/0007-measure-quota-gate-activation-before-ab-testing.md`.

Extend observation to 28 complete UTC days if:

- a high-impact tool/device/locale segment has fewer than 100 unique journeys;
- event coverage is unstable during the first 14 days; or
- the leading first-action/no-action category changes between the first and second seven-day periods.

This is an observation window, not an experiment.

## 9. Entry Conditions for Solution Stage

OP-001 may move from Investigation to Solution Definition only when all conditions below are met:

1. At least 14 complete UTC days and 200 unique eligible gate journeys have been observed.
2. At least 95% of cohort entries contain valid `tool_id`, `gate_instance_id`, `user_state`, `quota_mode`, `gate_reason`, and timestamp properties.
3. Duplicate or invalid event rates are quantified and do not change the ordering of the largest funnel losses.
4. At least 90% of gate journeys can be assigned to a valid first action or the derived no-action category.
5. `signup_started` delivery has been checked against `action=signup`, so measurement loss can be separated from behavioral loss.
6. The largest first-action/no-action branch is stable across two consecutive seven-day periods, or instability is explicitly documented as the reason not to proceed.
7. Any segment used to justify a solution contains at least 100 unique journeys; smaller samples cannot select a solution.
8. Successful Download within 24 hours is reported for every action branch using the same server authority.
9. The existing 84.08% New Account → Successful Download behavior is retained as a guardrail in later Solution evaluation.
10. The investigation report can state which measured step accounts for the largest loss without using inferred motives such as confusion, distrust, or price sensitivity.

If these conditions are not satisfied, status remains `INVESTIGATING` or becomes `BLOCKED BY DATA`; it does not advance to BUILD, REDESIGN, Pricing, Paywall, or A/B Test work.

## Investigation Deliverable

At the end of the observation period, produce one evidence table containing:

- Cohort size and event coverage.
- Primary funnel conversion and drop-off.
- First-action distribution.
- Successful Download rate by first action.
- Tool/device/locale/quota-mode segments meeting the sample threshold.
- Data-quality exceptions.
- Resolved and unresolved Unknowns.
- A binary recommendation: `READY FOR SOLUTION DEFINITION` or `CONTINUE INVESTIGATION`.

No solution concepts should be included in that deliverable unless the user separately authorizes the Solution stage.
